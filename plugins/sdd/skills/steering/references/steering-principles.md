# Steering Principles

Authoring philosophy for rules generated by the `steering` skill. Read before drafting any rule.

## Patterns over lists

Document patterns and principles, not exhaustive catalogs of files, components, or dependencies.

- Bad: list every file in a directory.
- Good: describe the organization pattern with one or two concrete examples.

## Single domain per file

One topic per rule file. If a file covers two domains, split it into two files.

## Imperative voice

Write rules as direct commands the agent can follow (for example, "Run tests with `cargo test`"), not descriptions or suggestions. State what to do, concretely.

## Concrete, project-specific detail

Show patterns with real commands, paths, and types from THIS project — not generic prose that could describe any codebase.

## Maintainable size

50–200 lines per file. If a file runs longer, it is probably cataloging instead of pattern-describing.

## Security first

Never include secrets, keys, passwords, tokens, or sensitive data in a rule.

## The Golden Rule

New code that follows existing patterns should NOT require a rules update. If a rule keeps needing updates, it is probably a list, not a pattern.

## Additive updates

On sync, preserve user content. Add, don't replace. When in doubt, propose an addition and let the user decide.
